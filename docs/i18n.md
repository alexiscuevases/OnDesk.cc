# Internationalization

Pulse serves the marketing site in multiple languages, each on its own indexable
URL. English is the default and stays unprefixed; every other language lives
behind a path segment.

```
ondesk.cc/pricing      → English  (default, no prefix)
ondesk.cc/es/pricing   → Spanish
```

## How it fits together

| Concern | Where |
| --- | --- |
| Locale registry, country map, path helpers | `src/i18n/config.ts` |
| Copy, one module per page per locale | `src/i18n/locales/<locale>/` |
| Lazy dictionary loading | `src/i18n/dictionaries.ts` |
| React context + `useI18n()` | `src/i18n/i18n-context.ts`, `src/i18n/context.tsx` |
| Region/browser detection | `src/i18n/detect.ts`, `functions/api/geo.ts` |
| `<html lang>`, title, canonical, hreflang | `src/i18n/seo.ts` |
| Routing | `src/routes/{-$lang}/route.tsx` |

### Routing

`{-$lang}` is a TanStack Router **optional path param**, so one route file serves
every language: `src/routes/{-$lang}/pricing.tsx` matches both `/pricing` and
`/es/pricing`. Adding a language does not add route files.

The layout route at `src/routes/{-$lang}/route.tsx` resolves the locale, loads
its dictionary in the route `loader` (so the page never renders half-translated),
and provides it through `I18nProvider`. It also:

- redirects `/en/*` → `/*` with a 301, so the default locale has exactly one URL
- throws `notFound()` for a prefix that isn't a shipped language

### The URL is authoritative

Whatever language the URL names is the language that renders. Detection never
overrides it and never triggers an automatic redirect — a link someone shares or
Google indexes always shows the language it promises.

Detection is used for exactly two things:

1. **A dismissible offer.** `LocaleHint` (`src/features/frontend/locale-hint.tsx`)
   asks `/api/geo` for the visitor's country (from Cloudflare's
   `request.cf.country`, falling back to `Accept-Language`) and offers a switch
   if it disagrees with the current URL. The offer is written in the language
   being offered.
2. **Remembering an explicit choice.** Picking a language in the switcher writes
   the `pulse_locale` cookie. That cookie always beats region detection, so
   someone who deliberately chose English while sitting in Mexico is never
   nagged again.

### Type safety

English is the source of truth. `Dictionary` is `typeof en`, and each locale
module is annotated with the matching type:

```ts
import type { CommonDict } from "../en/common";
const common: CommonDict = { /* ... */ };
```

A missing or misspelled key in a translation is a **compile error**, not a
runtime fallback. Verify with `npx tsc -b`.

## Adding a language

1. Add the code to `LOCALES` and `LOCALE_META` in `src/i18n/config.ts`.
2. If it maps to countries, add them to `COUNTRY_LOCALE` (and to the
   `SPANISH_COUNTRIES`-style set in `functions/api/geo.ts` if the edge should
   prefer it over `Accept-Language`).
3. Add a loader entry in `src/i18n/dictionaries.ts`.
4. Copy `src/i18n/locales/en/` to `src/i18n/locales/<code>/`, annotate each
   module with its `*Dict` type, and translate.
5. Add the currency symbol form to `USD_SYMBOL` in `src/i18n/format.ts`.
6. Run `npx tsc -b` — it lists every key you still owe.

No route or component changes are needed.

## Translating another page

1. Add `src/i18n/locales/en/<page>.ts` exporting the copy plus its `*Dict` type,
   and register it in `src/i18n/locales/en/index.ts`.
2. Mirror it under each other locale.
3. In the page component, replace hardcoded strings with `dict.<page>.*` from
   `useI18n()`, and add `useLocalizedSeo({ ...dict.meta.<page>, path, locale })`.

Conventions worth keeping:

- **Structure stays in code, copy moves to the dictionary.** Icons, hrefs, ids,
  ordering, booleans and prices live in the component, keyed by a stable `key`.
  A translation must not be able to break a link, a filter, or what a plan
  includes.
- **Split styled headlines into parts.** The editorial design prints one word
  inside an inverted block; translations move that word, so store
  `{ lead, highlight, trail }` rather than baking position into JSX.
- **Format numbers through `num()` / `usd()`** from `useI18n()`, never
  `toLocaleString()` — Spanish needs `99,99%` and `1.000`.
- **Leave machine-style tags alone.** `PULSE://INDEX`, `SIG.END`, `SUPPORT_OS`
  and `WIDGET.EMBED` are part of the visual language, not prose.
- **Prefer common-gender job titles** in Spanish ("Consultoría independiente",
  "Dirección de Operaciones") so testimonial personas aren't assigned a gender
  the English source never stated.

## Current status

Translated to Spanish:

- Site chrome — navbar, solutions dropdown, footer, language switcher
- Landing (`/`)
- Pricing (`/pricing`)
- Features (`/features`)

Reachable at `/es/*` but **still rendering English body copy** (Spanish chrome,
English content): about, blog, careers, changelog, contact, customers, help,
integrations, privacy, security, solutions (3 pages), status, terms.

Not localized at all yet:

- **Auth screens** (`/auth/*`) — they sit outside the `{-$lang}` tree, so
  `/auth` is listed in `UNLOCALIZED_PREFIXES` in `src/i18n/config.ts` and links
  to it are never prefixed. `AuthLayout` reads the `pulse_locale` cookie so
  "back to home" returns a visitor to their language, but the screens themselves
  are English. To localize: move `src/routes/auth*` under
  `src/routes/{-$lang}/`, and drop `/auth` from `UNLOCALIZED_PREFIXES`.
- **The console** (`/w/*`) — same mechanism will apply. Consider storing a
  per-user locale on the `users` table rather than relying on the cookie, since
  the console is authenticated.
- Transactional email (`functions/_lib/email.ts` hardcodes `<html lang="en">`).

## Known limitation: client-rendered `<head>`

The app is a client-rendered SPA, so `useLocalizedSeo` writes the title,
description, canonical and hreflang tags on mount rather than serving them in
the HTML. Crawlers execute JS and will read them, but two consequences follow:

- an unknown prefix like `/xx/pricing` returns HTTP 200 with a client-side
  "Not Found" (a soft 404) instead of a real 404 status
- social scrapers that don't run JS see the static `index.html` tags

If organic traffic to the localized pages becomes business-critical, inject
these tags at the edge with `HTMLRewriter` in a Pages Function — the locale is
derivable from the request path, so it needs no application state.
